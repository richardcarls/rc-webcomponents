# Styling

## Design-system neutral by default

Components ship without decorative visual opinions. The default appearance
mirrors the UA stylesheet; buttons look like buttons, inputs look like
inputs. This lets them blend into any design system without fighting existing
styles.

What components always emit is structural: layout, geometry, and interaction
state indicators. The decorative layer is entirely up to you.

## Color scheme

Components consume CSS system colors (`Canvas`, `CanvasText`, `ButtonFace`,
`Highlight`, etc.), which the browser resolves differently in light and dark
schemes. Set `color-scheme` on a container and every component inside it
adapts automatically:

```css
.my-app {
  color-scheme: dark;
}
```

No class-based theming or JavaScript needed for basic color scheme support.

## Global design tokens

The optional `base.css` export defines semantic tokens that all components
reference. Import it once at your application root to enable the token layer:

```css
@import '@rcarls/rc-webcomponents/themes/base.css';
```

These tokens fall back to CSS system colors without the import; the file is
optional. Override any token at your theme boundary to adjust all components
at once:

```css
:root {
  --rc-accent: oklch(55% 0.2 250); /* primary action color */
  --rc-border-color: oklch(75% 0 0); /* all component borders */
  --rc-control-block-size: 2.5rem; /* input / button height */
  --rc-control-radius: 0.5rem; /* border radius */
  --rc-font-family: 'Inter', sans-serif;
}
```

The semantic layer is deliberately smaller than the sum of every component's
styling API. Components consume these shared decisions and expose narrower
component tokens where their structure needs an additional adaptation point.

Set the popup and item type tokens at the theme root rather than on individual
elements. The same applies to a theme's menu and adaptive-menu tokens.
Custom properties inherit into shadow roots, so a menu rendered inside another
component's shadow root, where element selectors such as `.my-theme rc-menu`
cannot reach, still gets the theme's popup surface.

## Per-component tokens

Each component also exposes its own scoped tokens for fine-grained control.
These are documented in the API table on each component page. Example:

```css
/* Make the FAB match your brand */
rc-fab {
  --rc-fab-bg: oklch(55% 0.2 250);
  --rc-fab-color: white;
  --rc-fab-radius: 0.75rem;
  --rc-fab-shadow: 0 4px 12px oklch(55% 0.2 250 / 40%);
}
```

Some public tokens intentionally form a small family across related
components. `--rc-thumb-radius` aligns slider and range-slider thumbs;
`--rc-fab-*` tokens let `rc-fab-menu` reuse the FAB trigger contract. A few
composition tokens are deliberate pass-throughs: `rc-bottom-sheet` forwards
`--rc-dialog-scrim`, and `rc-fab-menu` forwards
`--rc-menu-button-popup-z-index`. These contracts are documented by every
component that consumes them and enforced by the architecture audit.

## CSS parts

Components expose named parts for styling elements that are inside shadow
DOM. Use the `::part()` selector:

```css
/* Style the trigger button inside rc-select */
rc-select::part(trigger) {
  font-weight: 500;
  letter-spacing: 0.01em;
}

/* Style the toggle indicator */
rc-select::part(toggle-indicator) {
  color: var(--rc-accent);
}
```

Available parts are listed in the API table under the **Parts** section on
each component's page.

## Styling hooks and ownership

Use the narrowest public styling surface that expresses the change:

1. Override a shared semantic token at a real theme ancestor when the decision
   should flow through nested light and shadow trees.
2. Override a component token on one component when changing a documented
   adaptation point such as geometry, color, or typography.
3. Use a CSS part when styling a shadow-owned element requires selectors or
   declarations that cannot be represented by one token.
4. Use a documented `data-rc-*` marker when consumer-authored light-DOM content
   must declare a structural or behavioral role.
5. Use a theme modifier class or theme-specific data attribute only for an
   optional visual recipe supplied by that theme.

The `data-rc-*` prefix identifies ownership, not visibility. Documented markers
such as `data-rc-icon`, `data-rc-field-control`, and
`data-rc-bottom-sheet-handle` are author-facing contracts. Other markers are
written by components or shared controllers for measurement, coordination, or
style deduplication and are not consumer APIs. Do not depend on a marker unless
the component or theme documentation explicitly exposes it.

Prefer native or ARIA state selectors such as `[open]`, `:checked`,
`[aria-selected]`, and `[aria-current]`. Components expose documented host
`data-*` state when the authoritative state cannot otherwise be selected by a
theme. Theme CSS may style that state, but it must not use CSS to create a
second behavioral source of truth.

Public tokens, parts, and documented markers are versioned API. The repository
architecture audit tracks their usage along with private theme overrides and
ID-selector complexity. Net growth requires a documented consumer need and an
explicit budget rationale; prefer consolidating an existing hook over creating
an overlapping one.

## Cascade layers

Shadow-DOM component styles are scoped by the shadow tree and do not share the
document's layer order. Components that must install structural light-DOM CSS
place it in the `rc-base` layer and deduplicate it per document or shadow root.
Consumer rules outside a layer therefore override these structural defaults
without selector specificity contests.

Each packaged theme declares its ordered layers after `rc-base`:

```css
@layer rc-base, rc-theme.defaults, rc-theme.bridge, rc-theme.native,
  rc-theme.components, rc-theme.css-components, rc-theme.overrides;
```

Naming `rc-base` first keeps component structural CSS below the theme even though
components inject it at runtime, after the theme stylesheet has loaded. A layer is
ordered by its first declaration, so without this an injected `rc-base` would become
the last and strongest layer. An application that declares its own layer order should
also list `rc-base` before the theme layers.

The real names include the theme package, such as
`rc-theme-material.components`. Defaults own the theme's raw source tokens,
the bridge maps those tokens to shared and component RC tokens. The opt-in
`native` layer is a convenience for styling ordinary HTML controls throughout
an application without composing every control from RC elements. Component
recipes can style native children when their presentation belongs to a themed
menu, toolbar, or other component context. `components` holds element-specific
recipes, parts, contextual selectors, and visual variants for registered RC elements.
The separate opt-in `css-components` layer styles native elements carrying documented
classes such as `.rc-button`, `.rc-chip`, `.rc-select`, `.rc-card`, and `.rc-list`,
plus `details.rc-disclosure`. These recipes provide appearance and CSS-visible states
only; they do not add behavior, events, popup replacement, or measured overflow.
Overrides hold the few contextual rules that must beat every component
variant, such as `rc-adaptive-menu` overflow rows, which restyle a moved `rc-button`
or `rc-menu-button` as a menu row whatever its own variant. Normal application rules
outside a layer outrank all theme layers, which provides a straightforward
consumer override path. Avoid routine
`!important`: important declarations reverse layer precedence.

This is also why a packaged theme's class belongs on a container, as shown
below, not on `<html>`. The shared `base.css` declares no layer at all, so
its `:root` values act as normal application rules and outrank every theme
layer for that same reason. On a container, a theme's own value is a direct
declaration that beats an inherited one regardless of layer; on `<html>`,
`:root` and the theme class target the same element, and `:root`'s
layer-free value wins outright.

### Native and CSS-only recipes

The native entrypoint keeps browser behavior and form semantics intact. The
CSS-only recipes add appearance and CSS-visible states to ordinary HTML; they
do not register elements or replace popups. Load a theme's defaults and bridge
when you want its token values, then opt into the two layers:

```css
@import '@rcarls/rc-theme-material/defaults.css';
@import '@rcarls/rc-theme-material/bridge.css';
@import '@rcarls/rc-theme-material/native.css';
@import '@rcarls/rc-theme-material/css-components.css';
```

`native.css` fills in controls that a component recipe does not style, including
consumer-authored controls inside toolbars, dialogs, cards, and rich popup
content. A component's themed presentation takes precedence for controls it
styles itself, such as menu rows and triggers. The boundary follows the
control's role in that component rather than every descendant of an RC host.
Add `data-rc-native="off"` to an element to opt it and its descendants out of
the native layer, for example when embedding a separately styled widget.

The same entrypoints exist for the [Substrate theme README](https://github.com/richardcarls/rc-webcomponents/blob/develop/packages/rc-theme-substrate/README.md),
[Material theme README](https://github.com/richardcarls/rc-webcomponents/blob/develop/packages/rc-theme-material/README.md),
[Tailwind theme README](https://github.com/richardcarls/rc-webcomponents/blob/develop/packages/rc-theme-tailwind/README.md), and
[Win31 theme README](https://github.com/richardcarls/rc-webcomponents/blob/develop/packages/rc-theme-win31/README.md). Supported
class recipes use native elements directly:

```html
<main class="rc-theme-material">
  <button class="rc-button" type="button">Save</button>
  <label class="rc-chip"><input type="checkbox" /> Filter</label>
  <div class="rc-chip-group"><button class="rc-chip" type="button">One</button></div>
  <label for="css-choice">Choice</label>
  <select id="css-choice" class="rc-select">
    <option>Choose one</option>
  </select>
  <textarea class="rc-textarea" aria-label="Notes"></textarea>
  <article class="rc-card">Card content</article>
  <ul class="rc-list">
    <li>
      <label><input type="checkbox" checked /> Selected item</label>
    </li>
  </ul>
  <details class="rc-disclosure">
    <summary>More</summary>
    <p>Details</p>
  </details>
</main>
```

Use `a[href].rc-button` or `a[href].rc-chip` for links. A checkbox or radio
inside `.rc-chip` remains in the document and is visually concealed only by
the recipe, so its label, keyboard focus, and form behavior remain native.
