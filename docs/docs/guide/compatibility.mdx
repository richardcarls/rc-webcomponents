# Compatibility and runtime

## Browser support

Core component packages, `rc-common`, and the aggregate component entry points share two
support tiers:

| Tier                      | Browser versions                                                                                               | Contract                                                                                                                                      |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Minimum validation target | Chrome 100+, Firefox 100+, Safari and iPadOS 15.4+                                                             | Components upgrade without errors and support their core form, keyboard, pointer, focus, and popup tasks. Newer visual effects may be absent. |
| Target support            | Current and previous stable desktop Chromium, Firefox, and Safari; current Chrome on Android and Safari on iOS | Full documented component behavior and base appearance.                                                                                       |

The minimum tier is a validation target until tests on those historical engines are recorded.
Current CI engines alone do not establish that guarantee. The minimum applies to the unthemed
components and their base styles. Theme, plugin, adapter, and framework integration packages
may specify their own opt-in requirements. A theme may need newer CSS for its intended visual
fidelity, smaller stylesheet, or performance without changing the core component tier.

The remaining validation work includes keyboard focus containment in carousel and page-turner
on engines without native `inert`, and visual checks for layouts that use custom states or
newer CSS. Use the target tier for applications that need these behaviors today.

Samsung Internet, embedded WebViews, other tablet browsers, and TV browsers receive feature-based
best-effort behavior. Their engine version, not the device name, determines which enhancements
are available. No particular model or remote-control interaction is guaranteed without a
recorded device test.

CI runs the complete component suite in Chromium, Firefox, and WebKit. WebKit is
the available cross-platform Safari engine check; release-critical mobile and
assistive-technology behaviors still require the manual matrix in
[Accessibility testing](./accessibility-testing).

Components feature-detect optional platform APIs and preserve a usable native
path when an enhancement is unavailable:

- **Progressive baseline:** meaningful native markup, form submission, label
  association, and ordinary links or controls remain available before upgrade
  or without JavaScript.
- **Upgrade:** the custom element adds the interaction promised by the applicable
  support tier. Below the minimum tier, only consumer-authored native markup is
  covered; successful upgrade is not guaranteed.

Component pages document narrower platform caveats. In particular, read the
mobile notes for [`rc-select`](../components/rc-select) and
[`rc-combobox`](../components/rc-combobox) before choosing a popup mode.

## Server rendering

Every package entry point imports in Node without a DOM: Lit's server build
supplies the `HTMLElement` and `customElements` shims, and no package touches
`document` or `window` while its module evaluates. The CI build checks every
entry point this way. A framework that evaluates client modules during a server
render, such as a React client component, can therefore import the packages.
Calling a `define` entry on the server registers the element with the shim and
has no other effect.

Rendering components on the server is a separate contract. The supported path
is native fallback markup from the server, with the elements upgrading once the
client loads their definitions. Every element also renders with Lit's server
renderer, including declarative shadow roots, and hydrates that output; CI
checks both for every element. The
[server rendering guide](./ssr) covers the stylesheets that keep the native
markup laid out before upgrade, and the current state of Lit server rendering.

Register components in a client entry point:

```html
<rc-select>
  <select name="status" aria-label="Status">
    <option>Draft</option>
    <option>Published</option>
  </select>
</rc-select>
```

```js
// Client-only entry point
import '@rcarls/rc-webcomponents/rc-select/define';
```

Frameworks that evaluate route modules on the server should place registration
behind their documented client-only boundary. The native child remains useful
until the browser loads and upgrades the custom element; this is progressive
enhancement, not component hydration.

## Import choice

Prefer the aggregate package's per-component subpaths. They keep dependency
management centralized without pulling unused components into the bundle:

```js
import '@rcarls/rc-webcomponents/rc-button/define';
import '@rcarls/rc-webcomponents/rc-select/define';
```

Use `@rcarls/rc-webcomponents/define` only when the application genuinely wants
to register the entire collection. Likewise, import classes from component
subpaths such as `@rcarls/rc-webcomponents/rc-select` instead of the root class
barrel when bundle size matters. See [Performance](./performance) for measured
sizes.

## Versioning

The collection is pre-1.0. Minor releases can contain intentional breaking API
changes, which are described by Changesets and release notes. Package versions
are locked together, so use one version across all `@rcarls/*` packages and
review migration notes before upgrading.
