# Server rendering

A server-rendered page can use `rc-webcomponents` today. The server sends the
native markup each component wraps, and that markup works on its own: links
navigate, forms submit, `<details>` opens, `<dialog>` shows. The elements
upgrade once the browser loads their definitions. See
[Compatibility](./compatibility#server-rendering) for the exact contract. This
guide covers the parts that make the window before upgrade look right.

## Imports are safe on the server

Every package imports in Node without a DOM. Server frameworks evaluate client
modules while rendering, so a module that imports a component, a type, or a
`define` entry no longer needs a dynamic import or a client-only wrapper just
to keep the server build from throwing. A `define` entry that runs on the
server registers the element with Lit's server shim and does nothing else.

`lit` is a peer dependency of every component package. Install it as a runtime
dependency of your app, not a development one, because the components import
it in production.

## Stylesheets for the first paint

Until an element is defined, the browser treats its tag as an unknown inline
element. Three stylesheets cover that state, and each is optional.

| Stylesheet                                            | What it does before upgrade                                                                                                                                         |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@rcarls/rc-webcomponents/themes/base.css`            | Defines the shared `--rc-*` semantic tokens.                                                                                                                        |
| `@rcarls/rc-webcomponents/themes/components-base.css` | Imports each light-DOM component's structural styles. These are the same rules the elements inject when they connect. Each package also exports its own `base.css`. |
| `@rcarls/rc-webcomponents/themes/pre-upgrade.css`     | Gives each shadow-DOM element the `display` it takes once defined, so blocks stack and grids lay out before the definition loads.                                   |

```css
@import '@rcarls/rc-webcomponents/themes/base.css';
@import '@rcarls/rc-webcomponents/themes/components-base.css';
@import '@rcarls/rc-webcomponents/themes/pre-upgrade.css';
```

All three put their rules in the `rc-base` cascade layer, below any theme. Load
them before your theme so the theme's layer order applies; the
[styling guide](./styling) explains the layers.

`components-base.css` uses `@import` with package specifiers, so it needs a
bundler or CSS tool that resolves packages, such as Vite, Next.js, or Tailwind
CSS. To link a single component's styles directly instead, use its own file,
for example `@rcarls/rc-button/base.css`.

### Skipping the runtime copy

A light-DOM component still injects its structural stylesheet when it
connects, unless the root already holds one. Mark a linked or inlined
stylesheet with `data-rc-light-dom-base` to say which components it covers:

```html
<link rel="stylesheet" href="/rc/button-base.css" data-rc-light-dom-base="rc-button" />
<link rel="stylesheet" href="/rc/components-base.css" data-rc-light-dom-base="all" />
```

The value is a space-separated list of tags, or `all`. A bundler that merges
these files into the app stylesheet drops the attribute, so the elements inject
their copy as well. The rules are identical and sit in the same layer, so the
duplicate costs only a few bytes of parsing.

## Register components on the client

Register the components a page uses in one client entry, rather than repeating
the list in every component that renders a tag. In a React app,
`@rcarls/rc-react` provides `RcRegister`, which a server component can render
because it takes plain tag names:

```tsx title="app/layout.tsx"
import { RcRegister } from '@rcarls/rc-react';
import './globals.css';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <RcRegister tags={['rc-app-bar', 'rc-card', 'rc-chip']} />
      </body>
    </html>
  );
}
```

Server components can then render `<rc-card>` and the other tags directly.
`RcRegister` loads each definition after hydration, so React has already
matched the server markup before any element upgrades and starts adding its own
attributes, such as `aria-controls` or a generated `id`. The
[React guide](./react#server-rendering-and-nextjs) covers the wrapper
components, which register themselves.

## Rendering with Lit's server renderer

Every element renders with [`@lit-labs/ssr`](https://lit.dev/docs/ssr/overview/), and
shadow-DOM elements render a declarative shadow root, so a page shows their structure
before any script runs. The CI build renders every element this way.

- On the server, elements cannot see their children, so anything they derive from a native
  child renders as if it were absent until the browser takes over.
- Server-rendered text uses each element's own `lang`, else the default set with
  `setServerLocale()` from `@rcarls/rc-common`. Set it to the page's `<html lang>`.
- Install a single copy of `@lit-labs/ssr-dom-shim`. If your package manager keeps an older
  copy for `lit` beside the one `@lit-labs/ssr` brings, nested elements fail to render with
  `getRootNode is not a function`; deduplicate it (`yarn dedupe @lit-labs/ssr-dom-shim`).

## Hydration

To have the elements adopt their server-rendered shadow roots rather than render new ones,
load Lit's hydration support before any element definition:

```js
// Client entry, before any define import
import '@rcarls/rc-webcomponents/hydrate-support';
import '@rcarls/rc-webcomponents/rc-card/define';
```

Each package keeps a server-render fixture for every element it defines, and CI renders it
on the server, hydrates it in a browser, and checks that the result matches a client
render. Every element passes except two, which still render correctly but keep a server
value after hydrating:

- `rc-textarea`: the line-number gutter keeps the line height measured over the server
  markup until the editor next re-measures.
- `rc-editor-toolbar`: internal to `rc-markdown-editor`, which hydrates it correctly; on its
  own it renders nothing until the editor configures it.

Hydration is not yet wired into a React framework. `@lit-labs/nextjs` is a webpack plugin
for Next.js 13 to 15, so a Next.js 16 app with Turbopack keeps the native-markup path above.
